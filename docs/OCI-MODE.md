# OCI mode (Oracle Cloud, Terraform)

The control plane runs on a small always-on VM; the game server runs on a separate x86 VM that the panel powers on and off on demand. When the game VM is stopped you pay only for its boot volume.

## Costs

- **Control plane**: `VM.Standard.A1.Flex` (Ampere ARM, 1 OCPU, 6 GB by default), which fits the Oracle Always Free allowance. A1 capacity is often exhausted in a region: if `apply` fails with "Out of host capacity", set `control_plane_shape = "VM.Standard.E2.1.Micro"`. Terraform does not retry shapes automatically.
- **Game server**: `VM.Standard.E5.Flex`, 4 OCPU / 24 GB by default. **This is a paid shape.** Billing for the compute stops while the instance is stopped; the boot volume (50 GB by default, `game_server_boot_gb`) and the backup bucket are billed all the time. Check current prices in the Oracle price list before applying.
- The panel raises the boot volume performance to 20 VPU/GB before a start and back to 10 at shutdown (`GAME_BOOT_ACTIVE_VPUS`, `GAME_BOOT_IDLE_VPUS`). It is best effort: an OCI error there does not block start or stop.
- If the game VM is left running with nobody playing it keeps costing money. Auto-stop (`IDLE_STOP_MINUTES`, default 20) and the offline watchdog (ASA never RCON-online for 90 minutes, `OFFLINE_WATCHDOG_MINUTES`) are the safety nets; do not disable both.

## Prerequisites

- An OCI tenancy with permission to create compute, networking, IAM (dynamic group and policy) and Object Storage resources, and service limits for the two shapes (check with `oci limits resource-availability get`).
- OCI CLI authenticated (`oci session authenticate` or `oci setup config`); verify with `oci iam region list`. Terraform's `oracle/oci` provider uses the same `~/.oci/config`.
- Terraform 1.5 or newer.
- A Supabase project with the migrations applied and Google OAuth enabled: steps 1 and 2 of [LOCAL-MODE.md](LOCAL-MODE.md#1-supabase-project). The Site URL is the panel's HTTPS address.
- Optional: a DNS name for the panel (`arksa_domain`); without it the certificate is self-signed.

## Steps

```bash
cd terraform
cp terraform.tfvars.example terraform.tfvars   # gitignored, never commit it
$EDITOR terraform.tfvars
terraform init
terraform plan                                  # always read the plan
terraform apply
```

Minimum values: `tenancy_ocid`, `region`, `ssh_public_key`, `supabase_url`, `supabase_publishable_key`, `supabase_secret_key`, `admin_emails`. Secrets end up in the Terraform state: use a protected or remote encrypted backend and never commit the state.

Useful outputs: `control_plane_url`, `control_plane_public_ip`, `game_server_instance_id`, `game_server_public_ip`, `backup_bucket`, `stop_game_server_command`, and the sensitive `agent_token` and `rcon_password` (`terraform output -raw rcon_password`). Both secrets are generated by Terraform and written to the VMs by cloud-init.

**The game VM is not stopped after `apply`** (`game_server_auto_stop = false`): on first boot the container downloads ASA (about 13 GB, 30-60 minutes). Watch it with `docker logs` on the VM or from the panel, and stop the VM with `stop_game_server_command` once the first start has completed. Setting `game_server_auto_stop = true` stops it right after `apply`, which interrupts that first install.

Then point the Google OAuth/Supabase settings at the panel URL, open it and sign in with the first address in `admin_emails`.

Open ports (NSG): UDP 7777 and 27015 from anywhere on the game server; RCON (27020), the agent (8787) and SSH only from inside the VCN; the control plane has 80/443 open and SSH.

## How it is wired

- Both VMs only run Docker. cloud-init writes the env files (`/etc/arksa/*.env`, mode 0600) and starts the images published by this repository's CI.
- The game VM has a systemd unit that, **at every boot**, downloads `docker/compose/game-server.compose.yml` from GitHub (`github_repo`, `github_ref`), pulls the image and runs `docker compose up -d`. This is how an on-demand host stays current without a push-based deploy. **If you fork, set `github_repo` to your fork** (the default is `GabryXnLab/ark-ascended-server`, ref `main`) and set `game_server_docker_image` / `control_plane_docker_image` to your own GHCR images. For private repos or packages set `github_token` (Contents read-only and Packages read).
- The VMs use an instance principal (dynamic group and policy created by the `iam` module): the panel starts/stops the game instance and the agent stops its own VM after the backup, with no static API keys.
- Backups go to the Object Storage bucket (`backup_bucket_name`, default `arksa-backups`), versioned, with lifecycle rules.

## Variables

The full list with defaults and descriptions is [`terraform/variables.tf`](../terraform/variables.tf); an annotated example is [`terraform.tfvars.example`](../terraform/terraform.tfvars.example). Main groups:

| Group | Variables |
|---|---|
| Account | `tenancy_ocid`, `region`, `compartment_ocid` (empty = tenancy root), `availability_domain` (empty = first), `ssh_public_key` |
| Naming | `project_tag`, `prefix` (default `arksa`) |
| Network | `vcn_cidr`, `subnet_cidr`, `create_vcn`, `existing_vcn_id`, `existing_subnet_id`, `create_control_plane_nsg` |
| Control plane | `manage_control_plane`, `control_plane_shape`, `control_plane_ocpus`, `control_plane_memory_gb`, `control_plane_docker_image`, `arksa_domain`, `supabase_url`, `supabase_publishable_key`, `supabase_secret_key`, `admin_emails`, `curseforge_api_key` |
| Game server | `game_server_shape`, `game_server_ocpus`, `game_server_memory_gb`, `game_server_boot_gb`, `game_server_boot_vpus`, `game_server_docker_image`, `max_players`, `server_password`, `game_server_auto_stop` |
| Deploy | `github_repo`, `github_ref`, `github_token` |
| Backups | `backup_bucket_name`, `backup_archive_days`, `backup_delete_days`, `backup_previous_versions_delete_days` |

To reuse a network and control plane that already exist (for example a host shared with other projects), set `manage_control_plane = false`, `create_vcn = false`, `create_control_plane_nsg = false`, `existing_vcn_id` and `existing_subnet_id`, and `vcn_cidr` to the real CIDR of that VCN. Terraform then manages only the game server resources.

## Operations

- **Changing settings after creation**: the game instance resource has `prevent_destroy = true` and ignores changes to `metadata` (cloud-init), image and shape, so that a later `apply` can never replace the VM and its boot volume. Consequently changing `max_players`, `server_password`, `github_repo` or the RCON password in Terraform does **not** reach an existing game VM: edit `/etc/arksa/game-server.env` (mode 0600) on the VM and recreate the container. `terraform destroy` of the game VM is refused until you remove that `lifecycle` block on purpose.
- **Rotate the RCON password**: replace `random_password.rcon_password` (`terraform apply -replace=random_password.rcon_password`, read the plan first), then set the same value as `RCON_PASSWORD` in `/etc/arksa/game-server.env` on the VM and recreate the container.
- **Update**: stop the VM; the next start pulls the newest compose file and images. The control plane VM updates with `docker pull` of the control-plane image and recreating the `arksa-backend` container.
- **Do not destroy the game VM** to restart it: stop and start. Game files, mods and saves live on the boot volume.
- **Remote state**: for several machines or sessions configure a remote backend (for instance OCI Object Storage through its S3-compatible API) in a `backend.tf` of your own.
